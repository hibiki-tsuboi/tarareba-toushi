# データ形式と計算

## 配置

実データのmanifestは `schemaVersion: 2`、`datasetVersion`、`isSample`、UTCのISO 8601 `publishedAt`、商品の `funds`、表記の `notices` を持ちます。IDは一意です。サンプルは形式1です。

| モード | manifest | 商品ID | 出典のkind |
|---|---|---|---|
| 通常の実データ | `live/manifest.json` | 一覧で決める（`all-country` など） | `official` |
| 開発用サンプル | `sample/manifest.json` | `demo-` で始まる10商品 | `synthetic` |

実データは `isSample: false` とHTTPSの出典URLが必要です。サンプルは `isSample: true` で、商品名と短い商品名に「サンプル」を含めます。設定モードに合わないID・出典・フラグは拒否し、キャッシュをモード別に分離します。どちらのモードも価格データを同梱せず、初回に公開URLから取得します。

`publishedAt` は配信データを作成した日時です。端末での取得日時や観測日の最終日とは異なります。実データの版が同じ場合は、確認し直しても作成日時を変更しません。

形式2の `path` は `funds/<id>.json` の固定パスです。`funds[].contentVersion` は `fund-` と商品内容のSHA-256（小文字16進数64桁）からなり、対応する履歴の `datasetVersion` と一致します。一覧全体の `datasetVersion` は英小文字・数字・ハイフンの1〜64文字、先頭は英小文字または数字です。履歴に加えて商品名・説明・分類・表記も含めたハッシュから作るので、それらを変えた場合も一覧全体の版が変わります（アプリは同じ版で中身が違う一覧を拒否します）。これらは変更を判別する情報で、ファイル名には使いません。形式1では従来の `funds/<id>.<datasetVersion>.json` を使い、一覧と履歴の版が一致します。

商品IDも英小文字・数字・ハイフンの1〜64文字で、先頭は英小文字または数字です。絶対URL、親ディレクトリ、パーセントエンコード、クエリ、別ドメインの指定は許可しません。HTTPリダイレクトはすべて拒否します。

形式2では商品の内容を変えたときだけ、その商品の識別子が変わります。日付が増えない最新価格の訂正も検知できます。配信側は全商品の履歴を検証します。アプリは一覧のうち自分が扱える商品（最大20商品）の履歴だけを取得・検証します。

固定URLの一覧・履歴は毎回再検証するキャッシュ設定です。アプリは一覧と履歴の更新情報が違う場合、一覧から1回だけ再取得し、再び一致しなければ以前の正常なスナップショットを保持します。

各系列は一覧と同じスキーマ・モード、対応する商品ID・通貨・系列の種類・更新識別子と、`valueBasis`、`source`、`observations` を持ちます。未知の追加キーは無視できますが、未知のスキーマは拒否します。

## 商品一覧

**どの商品を出すかは配信側が決めます。** アプリは商品IDも商品名も持たず、一覧に載った商品を載った順に出します。この並びがアプリでの並び・系列色の順で、先頭2商品が初回の選択です。

```json
{
  "id": "all-country",
  "displayName": "eMAXIS Slim 全世界株式（オール・カントリー）",
  "shortName": "オルカン",
  "summary": "日本を含む世界中の株式",
  "category": "株式",
  "currency": "JPY",
  "valueBasis": "nav",
  "path": "funds/all-country.json",
  "contentVersion": "fund-<64桁>",
  "firstDate": "2018-10-31",
  "lastDate": "2026-09-07"
}
```

| キー | 内容 |
|---|---|
| `displayName` | 正式名称。80文字以内。出典と並べて表示します |
| `shortName` | 画面での呼び名。20文字以内 |
| `summary` | 何に投資する商品かの一言。60文字以内 |
| `category` | 任意。選択画面の見出し。20文字以内。同じ分類の商品は続けて並べます。分類のない商品は「その他」にまとめ、どの商品にも分類がなければ見出しなしの一覧にします |
| `valueBasis` | 系列の種類。履歴の `valueBasis` と一致させます |

`notices` は配信元に求められた表記（登録商標など）で、各200文字以内・10件までです。アプリは「データと計算について」に配信されたまま表示します。出所の社名は各履歴の `source.name` から組み立てます。アプリには特定の運用会社の名前を書きません。

### 公開済みのアプリを壊さないために

公開したアプリは、その版の規則で一覧を読み続けます。1.0の規則は次のとおりで、配信側の変更をこの範囲に収めれば、公開済みのアプリは壊れません。

- 出すのは、アプリが扱える商品だけです（`currency: "JPY"` かつ `valueBasis: "nav"`、必須の項目がそろい、書式も正しいもの）。一覧の先頭から**20商品まで**出します。
- それ以外の商品（未知の `valueBasis`、円以外の通貨、読めない項目、21商品目以降）は、一覧全体を拒否せず**その商品だけ読み飛ばし**、履歴もダウンロードしません。選択画面には「アプリを更新すると、ほかに○商品から選べるようになります。」と数を出します（項目を読めなかった商品は数えません）。
- 一覧全体を拒否するのは、形式・モード・版・公開日時が不正なとき、IDが重複するとき、扱える商品が1つもないときだけです。
- 商品を外す・並べ替える・名前や説明を変えるのは、配信だけでできます。保存済みの選択から消えた商品は外れ、1つも残らなければ先頭2商品に戻ります。
- **新しい種類の商品は、新しい `valueBasis`（または通貨）で表します。** 既存の `nav` の意味や既存の項目の型を変えてはいけません。公開済みのアプリが誤った計算をします。
- **新しい種類の商品は、それを計算できるアプリを公開してから配信します。** 先に配信すると、公開済みのアプリには出ないうえ、最新版のアプリでも選べません。
- 1.0は扱える商品の履歴をすべてダウンロードします（1ファイル2MiBまで、端末への保存は合計42MiBまで）。商品を大きく増やすときは新しいアプリ用に別の一覧URLを用意し、`live/manifest.json` は1.0が扱える形で配信し続けます。

配信側の `contract.mjs` はアプリより厳しく、現在のアプリが出せない商品を含む一覧、21商品以上の一覧、分類が途切れる並びを公開前に拒否します。新しい種類を配信するときは、それを計算できるアプリを公開した後で、`contract.mjs` とこのドキュメントを更新します。

以下は形式1の開発用サンプルの系列です。

```json
{
  "schemaVersion": 1,
  "datasetVersion": "sample-v1",
  "isSample": true,
  "fundId": "demo-all-country",
  "currency": "JPY",
  "valueBasis": "reinvestedIndex",
  "source": {
    "kind": "synthetic",
    "name": "開発用に生成した架空の比較データ",
    "url": null,
    "note": "実際の運用実績ではありません"
  },
  "observations": [{"date": "2025-01-06", "value": "10000.000000"}]
}
```

## 日付と値

- 日付は1900〜2200年の実在する `YYYY-MM-DD`。昇順・重複なし。先頭と末尾がmanifestの `firstDate` / `lastDate` と一致する必要があります。
- 観測値は正の10進数文字列。整数部12桁以内、小数部6桁以内。指数表記、NaN、負数、0は禁止です。最大30,000観測/商品、HTTP応答は2MiB/ファイルまでです。
- `nav` は通常の基準価額（1万口あたり・信託報酬控除後）です。実データの新規生成はこの系列だけを使います。観測値は日付と基準価額だけを持ち、分配金の受取額・再投資は含めません。分配金が出た場合の表示損益は、受取分を含む投資全体の損益とは異なります。
- `reinvestedIndex` は開発用の架空サンプルの系列名で、実データでは使いません。旧版キャッシュ向けに残していた `reinvestedIndex`（監査済みの版だけ）と `navWithoutDistributions` の読み込みは、2026-09-28に一覧へ商品ごとの `valueBasis` を加えた際に削除しました。旧版の一覧はこの項目を持たないため、どのみち読めなくなったためです。

## 共通期間と計算

開始日は指定日以降の最初の共通観測日、終了日は最後の共通観測日です。共通観測日は**選択した商品だけ**の積集合で求めます（未選択の商品は比較期間に影響しません）。指定日がいずれかの履歴開始前、または共通終了後なら計算しません。共通日がない場合も拒否します。開始＝終了は元本と同額、損益0です。同時に比較できるのは8商品までで、3商品以上では差額の代わりに順位と最大差を表示します。

投資のしかたは**一括投資**と**毎月積立**の2つです。端末に保存する入力値（UserDefaultsの `comparison.input.v1`）は `plan` に `lumpSum` / `monthly` を持ち、キーのない旧版の入力は一括投資として読みます。入力金額は、一括投資では元本の全額、毎月積立では1回分の積立額です。

### 一括投資

開始日に全額を購入します。

```text
評価額(t) = 元本 × 系列値(t) ÷ 系列値(開始日)
損益(t) = 評価額(t) − 元本
損益率(t) = (系列値(t) ÷ 系列値(開始日) − 1) × 100
```

### 毎月積立

指定日と同じ日付に毎月購入します。

- 日付は毎回指定日から数えます。31日を指定すると、2月は月末日（28日か29日）、3月は再び31日です。
- 購入日は、その日付以降で最初の共通観測日です。休場日などは次の共通観測日に回り、選択商品はすべて同じ日に購入します。1回目の購入日は開始日と一致します。
- 予定日が最後の共通観測日より後の回は含めません。
- 共通観測日がないまま次の予定日を過ぎた場合、その間の回はまとめて次の共通観測日に購入します。回数と元本は予定どおり数えます。

```text
元本(t) = 積立額 × t までの購入回数
評価額(t) = Σ[t までの各回] 積立額 × 系列値(t) ÷ 系列値(購入日)
損益(t) = 評価額(t) − 元本(t)
損益率 = (評価額 ÷ 元本 − 1) × 100
```

評価額は購入日ごとに繰り越して求めます。直近の購入日の評価額に系列値(t)を掛けてから系列値(直近の購入日)で割り、購入日にはその日の回数分の積立額を足します。掛けてから割るため、1回しか購入しない場合は一括投資と同じ式になります。購入した回はその日に払った額で評価されます。

### 一括との比較

毎月積立の結果には、同じ元本を開始日にまとめて投資した場合の評価額を商品ごとに並べます。元本の全額を開始日に用意できたと仮定した比較です。購入日が開始日しかない場合（開始日が最後の予定日にあたる場合や、全回が最初の共通観測日を待った場合）は同じ購入になるため表示しません。

```text
一括の評価額 = 元本(終了日) × 系列値(終了日) ÷ 系列値(開始日)
差 = 一括の表示評価額 − 積立の表示評価額
```

一括の評価額は一括投資と同じ式・同じ演算順で求めます（一括投資の結果では評価額と桁まで一致します）。差は1円に丸めた表示評価額どうしで求め、正なら一括、負なら積立のほうが多い結果です。

### いちばん沈んだとき

商品ごとに、期間中でその日の損益がもっとも小さかった日と、その額を出します。同じ額の日が複数あれば早い日を選び、一度も負にならなければ「元本割れなし」とします。一括との比較では、同じ元本を開始日に入れた系列にも同じ方法で求めます。

```text
その日の損益(t) = 表示評価額(t) − 元本(t)
いちばん沈んだとき = その日の損益(t) が最小かつ負の t
```

表示評価額（1円に丸めた値）で比べるので、1円未満だけ元本を下回った日は元本割れとして扱いません。毎月積立の元本(t)はその日までに購入した回の合計で、購入日の積立額はその日に払った額で評価されます。高値からの下落率（いわゆる最大ドローダウン）ではなく、払った額に対していちばん大きく下回った額です。

### 丸めと対象外

内部はDecimal。表示評価額を1円単位で四捨五入し、表示損益＝表示評価額−元本、表示差額＝Bの表示評価額−Aの表示評価額とします。毎月積立の元本は終了日までの積立額の合計です。表示上の同額は勝者なし。率は小数1桁。税金・購入換金手数料、分配金の受取額・再投資は除外し、整数口数への丸めはしません。

## サンプルの再現性

生成はネットワーク不要で、開始・終了・seed・versionが同じなら同一です。平日の架空時系列であり、日本の祝日カレンダーや実績を再現しません。生成先は `public/sample/` のみです。固定フィクスチャはSwiftのテストターゲットに置き、UIテストではランナーから応答を渡します。`npm run validate` は配信JSONの契約に加えて、アプリのソース配下に価格データファイルがないことも確認します。
